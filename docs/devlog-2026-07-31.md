# Development log — 2026-07-31

## Scope and starting point

This tranche hardens the Pingo VDU bridge and its ownership boundaries. It is
not a renderer optimization and does not supersede the qualified rendering
work at the starting commit.

2. Starting commit: `1add03f` (`Harden Pingo uploads, clipping, and depth`).
3. Inherited sources: `CODEX_PINGO_HANDOFF.md`, dated 2026-07-30, and the
   read-only `PINGO_Z_SCALE_BUG_NOTE.md`, dated 2026-07-29.

   the starting point. The inherited findings were follow-up robustness work,
   not grounds for rolling back the renderer.

## Corrections implemented

1. Corrected the single-axis Z-scale setters.

   Pingo object subcommand 8 and scene subcommand 28 now write `m_scale.z`.
   Their Y components remain unchanged. A real byte-stream integration test
   covers both commands and their three-axis predecessors.

2. Made control initialization atomic.

   Dimensions must be nonzero and representable by the VDP bitmap type.
   Pixel and byte products are checked before allocation. The private frame,
   depth buffer, mesh map, and object map are staged locally; any failure
   releases every successful allocation. The validity tag and size are
   published only after the complete control is renderable.

3. Implemented complete, idempotent teardown.

   Teardown invalidates the control first, then releases object-owned UV
   arrays, retained texture bindings, every mesh array, both maps, the depth
   buffer, and the private frame. Explicit subcommand 39 now uses the
   canonical buffer-clear route.

   A registry contains only controls that completed initialization. Generic
   mutation and destruction paths deinitialize a registered control before
   changing its bytes. Deep-copied control bytes are not authoritative.
   Zero-copy reference copying rejects a live control; spreading a control
   deinitializes it before publishing aliases. The latter work also repaired
   a pre-existing generic self-spread iterator/use-after-free by reacquiring
   the source map entry after a target clear may have erased it.

4. Made live control buffers opaque where ordinary buffer interpretation is
   unsafe.

   Buffered call/jump and callbacks cannot execute control bytes as VDU
   commands. A live control cannot become bitmap, texture, render-target,
   font, font-character-pointer, audio-sample, or affine-transform data.
   Output redirection and all in-place buffer writers teardown first. This
   prevents owner pointers from being executed, overwritten, retained as
   unowned typed data, or exposed as a writable render target.

5. Defined texture lifetime without per-bind pixel copies.

   Each object binding retains both the VDP `Bitmap` wrapper and the exact
   `BufferStream` that owns borrowed pixels. Clearing or replacing the bitmap
   ID therefore leaves the already-bound snapshot valid. An explicit
   successful object rebind adopts the replacement; a failed allocation keeps
   the previous binding and mesh association unchanged. Control teardown
   releases all retained owners.

6. Made uploads transactional and bounded on truncation.

   Vertex, index, mesh-UV, texture-index, and object-UV replacements are
   staged. A failed read or allocation preserves the previous arrays, derived
   validity, cached bounds, and owned-allocation count. A structurally or
   allocation-rejected command still consumes a complete declared payload to
   keep the next command aligned. If the payload is truncated, the first
   missing word ends the operation after one communications timeout; it does
   not repeat that timeout for every absent element.

   No arbitrary protocol ceiling was added. Every 16-bit element count,
   including 65,535, remains legal when memory and payload are available.

7. Added deterministic bridge qualification.

   Userspace-only allocation hooks can fail the next selected Pingo-owned
   allocation and report the exact live allocation count. The new
   `pingo_bridge_robustness_test.cpp` drives the real VDU byte stream and uses
   general-poll or render-completion packets as ordering barriers. It covers
   Z scale, each initialization allocation, texture clear/replacement/rebind,
   explicit/generic/global teardown, repeated populated lifecycles,
   copied/aliased/repurposed control isolation, call/jump and bitmap-target
   rejection, all five upload allocation failures, truncation at several
   offsets, maximum-count recovery, and immediate next-command alignment.

## Behavioral boundaries retained

1. Pingo render-completion subcommand 41 is unchanged.
2. Buffered callback commands `0x50`/`0x51` do not provide a generic
   “operation finished” protocol and are not a substitute for subcommand 41.
   A general next-command-complete notification remains separate future
   protocol work.
3. A copied block containing a plausible control tag and pointers is not a
   control. Successful initialization plus registry membership is the
   authority.
4. Bitmap metadata queries would be useful, but size/format information alone
   cannot pin or invalidate borrowed texture storage.
5. The shared-edge and near-coplanar depth stress fixture remains separate
   future renderer work.

### `CODEX_PINGO_HANDOFF.md` (2026-07-30)

> # Codex handoff: Pingo bridge concerns
>
> Date: 2026-07-30  
> Branch reviewed: `experiment/hecker-rasterizer`  
> Reviewed commit: `1add03f` (`Harden Pingo uploads, clipping, and depth`)
>
> This is a focused handoff for the next Codex session working on the custom
> Pingo VDP. It records bridge and lifecycle concerns found during a read-only
> architecture review. It is not a request to redesign Pingo, and this branch
> is reference material rather than the intended base for the separate Wolf3D
> VDP work.
>
> The current branch passes the Pingo command-surface guard and the ordinary
> native smoke suite. The concerns below are therefore follow-up robustness
> work, not evidence that the qualified renderer should be rolled back.
>
> ## 1. Fix and cover the single-axis Z-scale setters
>
> `PINGO_Z_SCALE_BUG_NOTE.md` contains the focused report. The defect is still
> present in `video/pingo_3d.h`: both `set_object_z_scale_factor()` and
> `set_scene_z_scale_factor()` assign the converted value to `m_scale.y` rather
> than `m_scale.z`. Their three-axis counterparts assign Z correctly.
>
> Treat this as a small independent correction:
>
> 1. Add bridge-level coverage for object and scene subcommands 8 and 28.
> 2. Confirm that Y is unchanged and Z receives the requested scale.
> 3. Change only the two assignments.
> 4. Run the command-surface guard, native smoke checks, emulator fixture, and
>    required physical/human validation before committing.
>
> ## 2. Complete control teardown
>
> `Pingo3dControl::deinitialize()` is empty, but subcommand 39 calls it before
> removing the control buffer. The control owns more than the buffer containing
> its C++ object:
>
> - `m_frame` and `m_zeta` PSRAM allocations;
> - the `m_meshes` and `m_objects` maps;
> - PSRAM arrays referenced by mesh positions, indexes, and texture coordinates;
> - object-owned texture-coordinate arrays.
>
> Erasing the control buffer without releasing those resources leaks memory and
> can leave borrowed pointers conceptually live. Implement explicit, complete,
> idempotent teardown. Exercise create/delete cycles under leak or allocation
> accounting, including partially initialized controls.
>
> ## 3. Define bitmap lifetime and invalidation
>
> `create_object()` binds `Texture::frameBuffer` directly to a VDP bitmap's
> `data` pointer. This is efficient and appropriate for rendering, but the bridge
> does not establish what happens when that bitmap or its backing buffer is
> cleared, replaced, resized, or reformatted. A Pingo object can consequently
> retain a dangling pointer.
>
> Choose and document one ownership rule:
>
> - retain/pin the bitmap storage while an object references it; or
> - receive bitmap lifecycle notifications and invalidate/rebind affected
>   objects before rendering.
>
> Do not solve this by copying every texture unless measurements justify that
> cost. Add a native bridge test that binds a texture, replaces or deletes its
> bitmap, and then attempts to render without dereferencing stale storage.
>
> ## 4. Bound malformed or truncated uploads
>
> Mesh uploads correctly stage replacements and preserve prior valid data on
> failure. However, handlers still drain the declared element count by repeated
> `readWord_t()` calls. A large count paired with a truncated serial payload can
> therefore multiply timeout latency and hold the VDP task for an excessive
> period.
>
> Add a defensible bound or abort strategy before allocation and draining. It
> must preserve stream synchronization for valid commands and fail closed for
> invalid input. Cover oversized counts, truncated payloads at several offsets,
> and recovery by the next valid command.
>
> ## 5. Make initialization failure atomic
>
> `initialize()` publishes the control tag and size before all owned allocations
> are known to have succeeded. Failed `m_frame` or `m_zeta` allocation currently
> logs the error but can leave a control that passes `validate()`. Width and
> height also originate as 16-bit protocol values, so pixel-count and byte-count
> arithmetic must be checked before allocation.
>
> Initialization should either produce a fully renderable control or release all
> partial resources and leave no valid control buffer. Add checked multiplication
> for frame and depth sizes, allocation-failure injection, and tests covering
> failure at each allocation step.
>
> ## 6. Render-complete notification should not stay a Pingo-only mechanism
>
> Pingo subcommand 41 (render-complete) is a one-off notification bolted onto
> this subsystem. The protocol has no general callback/notify primitive for the
> VDP to signal MOS asynchronously — `BUFFERED_ADD_CALLBACK`/
> `BUFFERED_REMOVE_CALLBACK` (`0x50`/`0x51`) exist, but nothing in the current
> callback machinery covers "tell me when this async operation finishes." That
> gap predates Pingo and has been a longstanding, repeatedly-raised complaint
> about the protocol in general, not something specific to this bridge.
>
> If/when a general async-completion callback lands upstream, subcommand 41
> should be retired in favor of it rather than kept as a parallel path. It's
> also worth us evaluating implementing that general mechanism ourselves as part
> of the Wolf3D VDP work, both because we need it and because closing this gap
> has standalone value. Don't fold this into the Z-scale/teardown/lifetime/
> upload fixes above — it's a separate, larger design question and should be
> scoped independently.
>
> For now, do not build on `0x50`/`0x51` (command 80/81) as a substitute — the
> event-type enum is fixed and does not cover "an arbitrary VDP operation just
> finished," so Pingo subcommand 41 stays as-is until a real replacement
> exists. That replacement is a strong candidate for its own upstream pull
> request as a first-level VDU command in its own right (not just a Pingo
> concern) — it's generically useful enough to be worth proposing on its own.
> One workable general shape: "when the next full command finishes executing,
> notify that it is done" — i.e. a generic completion notification tied to
> command execution rather than to any specific subsystem. This note is being
> kept in both this repo and the Wolf3D VDP research devlog, since it's
> relevant to both projects.
>
> ## 7. Upstream watch: issue #340, winding-rule triangle fill
>
> [AgonPlatform/agon-vdp#340](https://github.com/AgonPlatform/agon-vdp/issues/340)
> (Steve Sims) proposes a winding-rule-aware variant of the triangle-fill PLOT
> op, motivated by back-face culling for VDP-side 3D triangle rendering — the
> matrix-transform pipeline is already in the VDP, and back-face culling is
> called out there as "a significant missing piece." Two shapes are floated: a
> new dedicated PLOT op, or a VDP variable the existing triangle-fill op would
> obey.
>
> Relevant to Pingo because it currently does its own winding/culling work on
> the eZ80/native side (see the frustum/winding correctness controls in
> `pingoasm/docs/pingo-renderer-optimization-todo.md` phase 0.5). If the VDP
> grows native back-face culling for triangle fills, that's a future candidate
> for offloading part of Pingo's per-triangle work upstream. Not implemented
> yet — this is a watch item only, no action needed now.
>
> ## 8. Upstream watch: issue #335, bitmap/sprite info query
>
> [AgonPlatform/agon-vdp#335](https://github.com/AgonPlatform/agon-vdp/issues/335)
> (Steve Sims, opened Nov 12 2025, last comment Jan 2, still open, no PR) asks
> for VDP variables to read back info on the currently selected bitmap/sprite —
> size, format, and for sprites x/y, hardware-sprite flag, plot mode. Currently
> only minimal state (selected bitmap ID, bitmap count, selected sprite ID,
> sprite count, active transform buffer ID) is exposed.
>
> Relevant to item 3 above (bitmap lifetime/invalidation): being able to query a
> bitmap's current size/format from the VDP side is a building block for
> detecting resize/reformat rather than only guarding against it structurally.
> Also relevant to the separate Wolf3D VDP work, which will own many wall/sprite
> textures on the VDP side and would benefit from querying bitmap state instead
> of shadow-tracking it on the eZ80. A good, wanted-by-us candidate to
> eventually implement and contribute upstream — marked as a followup for when
> it becomes relevant to either project, not started, no comment posted.
>
